# Lean

Written on 2026-11-06. How a rule's obligations are checked in Lean, as a second checker beside cvc5 and Ethos. Tracked by [CRO-67](https://linear.app/cronch-ai/issue/CRO-67).

## Status

Decided by the owner on 2026-11-06 (in a comment on CRO-67):

- The first Lean target is **exported rule queries, with their proofs checked in Lean**.
- That gives a **second checker, independent of cvc5 and Ethos**.
- A reference semantics in Lean comes later.

Everything below that says how is proposed, and not yet seen by the owner.

## Why

A rule's proof is checked by Ethos today ([Rules](2026-11-05-rules.md#how-a-proof-is-tied-to-its-query)). Ethos and its CPC signatures come from the cvc5 project, so a bug shared by the prover and the checker goes unseen. CRO-61 also showed how much of the checking rests on `check.mjs`'s allowlist rather than on Ethos.

Lean's kernel is small, widely used and independent of any solver. A proof it accepts was checked by a kernel that doesn't care how the proof was made (A2), and anyone can recheck it with Lean alone (F6).

## The shape

1. **The kernel exports each obligation as a Lean statement**, from the same `Script` it prints as SMT-LIB. A second printer reads the same data, so the encoder stays one piece of trusted code, not two.
2. **A proof is a Lean file** that proves that statement. Whoever writes it, an agent or a person, may use any tactic.
3. **A checker ties the proof to the statement.** It accepts only a theorem whose type is the exported statement, and that uses only Lean's standard axioms.

Nothing in this path runs cvc5 or Ethos. The two checkers can then be used one at a time or together.

### The statement

An obligation is a refutation today: a query is `unsat` when the rule holds. In Lean, the obligation is stated the other way round: its query's assertions can't all be true. `ruleObligations` with `format: "lean"` writes it as a module that defines the statement, with no proof:

```lean
import Cronch.Smt

open Classical

structure «record:8742a65a» where
  «record:8742a65a#make» ::
  «record:8742a65a.url» : String
  deriving Inhabited
export «record:8742a65a» («record:8742a65a#make» «record:8742a65a.url»)
-- ...

abbrev statement : Prop :=
  ∀ («v:args» : «record:8742a65a») («v:grant» : «record:2e5c7a65»),
    ¬ ((«v:grant» = («record:2e5c7a65#make» ([] : (List String)))) ∧
      (Smt.seq.contains («record:2e5c7a65.netAllow» «v:grant») [(«record:8742a65a.url» «v:args»)]))
```

A proof is a `theorem` whose type is `statement`. The printer ([lean.rs](../crates/kernel/src/smtlib/lean.rs)) reads the same `Script` the SMT-LIB printer does, one part for one:

| SMT-LIB                       | Lean                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------- |
| `Int`, `String`               | `Int`, `String`                                                                 |
| `Bool`                        | `Prop`, with `open Classical` for `if`                                          |
| `(Seq t)`                     | `List t`                                                                        |
| `declare-datatype` (a record) | a `structure`, its constructor and selectors exported under their SMT-LIB names |
| `declare-const`               | a variable bound by the statement's `∀`                                         |
| `assert`                      | a conjunct under the `¬`                                                        |
| `let`, `ite`, `forall`        | `let`, `if`, `∀`                                                                |
| an operation                  | the same name under `Smt`, as `Cronch/Smt.lean` defines it                      |

Reading `Bool` as `Prop` puts the query's connectives and quantifiers in Lean's own logic, which is where its tactics work.

`Cronch/Smt.lean` defines SMT-LIB's operations over these types: `seq.contains`, `seq.extract`, `str.from_int`, `str.prefixof` and the rest. Each agrees with SMT-LIB wherever an export can use it:

- **`div` and `mod` are Euclidean,** as `Int.ediv` and `Int.emod` are. A refutation never holds a partial operation (the kernel refuses it), so neither is used with a zero divisor, where SMT-LIB leaves them unspecified.
- **`seq.nth` is used only within `0 ≤ i < seq.len s`,** under the quantifier that says a list's items are values the kernel holds. Outside that, SMT-LIB leaves it unspecified and `Smt.seq.nth` gives `default`, which no statement can see.
- **SMT-LIB's characters are code points up to `0x2FFFF`.** Lean's `Char` is any Unicode scalar value. A kernel string is a JSON string, which Lean's `String` covers exactly. So the Lean statement quantifies over the strings the kernel can hold, which the SMT-LIB query doesn't quite. A proof in Lean is then about the kernel's strings, not SMT-LIB's.

**What has no Lean reading yet is refused** with `{ kind: "lean", what }`, never approximated: a `Float`, a variant, a recursive function, an uninterpreted one. No rule obligation T1 makes needs one.

### The checker

A proof file can run code while Lean elaborates it, and can try to change what names mean. So the checker trusts only the exported statement:

1. The kernel's export is the **challenge**: the statement, with `sorry` as its proof.
2. The proof file is the **solution**: the same theorem name, with a proof.
3. **[Comparator](https://github.com/leanprover/comparator)**, the Lean FRO's tool for exactly this, checks that each theorem has the challenge's statement, and uses only the permitted axioms: `propext`, `Quot.sound` and `Classical.choice`. It builds the solution in a sandbox.

That refuses `sorry`, a new `axiom`, and `native_decide`, which adds `Lean.ofReduceBool`. The never-introduce rule for `sorry`, axioms and `admit` is then enforced by the checker, not by review.

`proofs/lean.test.mjs` keeps the attacks, as `rules.test.mjs` does for Ethos:

- a proof of another statement;
- `sorry`, `admit`, an `axiom`, `native_decide`;
- a proof that redefines a name from `Cronch/Smt.lean`;
- a proof that changes a notation or an instance before its theorem.

### Where it lives

A Lake project at `kernel/lean/`, with its toolchain pinned in `lean-toolchain`. CI installs it with `elan`, as it installs cvc5 and Ethos into `.proof-tools`.

## Proposed decisions

1. **Proofs are written in Lean, not reconstructed from cvc5's.** [lean-smt](https://github.com/ufmg-smite/lean-smt) reconstructs cvc5's proofs in Lean, but only for uninterpreted functions and linear arithmetic, with quantifiers. Strings, sequences and datatypes, which every rule query uses, are future work there. A reconstruction would also tie the Lean proof to cvc5's search, which is less independent.
2. **Lean joins Ethos; it doesn't replace it yet.** A rule's verdict names the checker that accepted its proof ([Claims](2026-11-06-claims.md#the-shape)). A rule can require either checker or both. Whether Ethos stays is decided once Lean covers every obligation the tests make.
3. **The kernel exports; it doesn't run Lean.** It writes statements, as it writes queries, and takes no part in checking them. `ruleObligations` gains a `format: "lean"`. Its SMT-LIB output doesn't change.

## What a proof rests on

What it rests on with Ethos (see [Rules](2026-11-05-rules.md#what-a-proof-rests-on)), except:

- **Ethos and its CPC signatures** are replaced by **Lean's kernel, Comparator and its sandbox**.
- **`Cronch/Smt.lean`** is added: it must say what SMT-LIB says. A bug there gives a valid proof of the wrong statement, as an encoder bug does today. It belongs in the Pata spec beside the encoding.

## The spike

[CRO-86](https://linear.app/cronch-ai/issue/CRO-86), on 2026-11-06, with Lean 4.35.0. The four T1 obligations are written in Lean by hand in [`lean/Spike/T1.lean`](../lean/Spike/T1.lean), beside the queries they were written from: `initial` and `net.ask.onResult` for each of `net.fetch` and `shell.online`.

- **`grind` closes all four**, one line each, once `Cronch/Smt.lean` gives it one lemma: containing a one-element sequence is membership (`contains_unit`, tagged `@[simp, grind =]`). Without it, `grind` closes the two `initial` obligations and not the two `onResult` ones.
- **Each proof uses only `propext`, `Classical.choice` and `Quot.sound`.** `simp` alone closes the `initial` ones with fewer axioms. `decide` closes none: the statements quantify over strings.
- **`grind` fails on a false obligation.** A rogue update that adds the URL whatever the answer gives an obligation `grind` can't close, as it should.
- **The build takes about a second.**

| Obligation                | `grind` | `grind` without the lemma | `simp` | `decide` |
| ------------------------- | ------- | ------------------------- | ------ | -------- |
| `net.fetch` `initial`     | yes     | yes                       | yes    | no       |
| `net.fetch` `onResult`    | yes     | no                        | no     | no       |
| `shell.online` `initial`  | yes     | yes                       | yes    | no       |
| `shell.online` `onResult` | yes     | no                        | no     | no       |

So the rest of the plan is worth doing, with one addition: **`Cronch/Smt.lean` ships the lemmas that make SMT-LIB's operations usable by `grind`**, not only their definitions. Those lemmas are proved in Lean, so they add nothing to what a proof rests on.

T1's obligations are small: propositional structure over list membership. They say little about obligations with arithmetic, `seq.nth` or quantifiers, which T1 doesn't have.

### Checking in a Worker

Full Lean can't run in a Worker: the toolchain is hundreds of megabytes, and `grind` needs its elaborator. Checking needs neither, only a Lean kernel, much as [z3-wasm](https://github.com/cronch-ai/z3-wasm) builds only the parts of z3 the platform calls.

**nanoda fits.** [CRO-91](https://linear.app/cronch-ai/issue/CRO-91)'s spike, on 2026-11-06, built [nanoda](https://github.com/ammkrn/nanoda_lib), an independent Lean kernel in Rust that Comparator can already use, for `wasm32-unknown-unknown`:

- It needed two of nanoda's functions made public, and checks serially, from bytes in memory, with no threads or files.
- The module is 840 KB and imports nothing.
- Each T1 proof, exported with `lean4export` (0.9–1.3 MB, about 600 declarations), checks in under 60 ms and 12 MiB, against a Worker's 128 MB.
- `sorry` and a new `axiom` are refused as unpermitted axioms.
- A proof replaced by its own statement traps.

**The statement is pinned by the platform** (decided by the owner on 2026-11-06). Comparing a proof with its statement needs the statement as Lean's kernel sees it: an export of the challenge. Only Lean's elaborator can make one from the kernel's Lean text, and it can't run in a Worker. So:

1. When a rule is registered, a trusted job outside the Worker elaborates each of its statements with full Lean, as `check-lean.mjs` writes the challenge, and exports it. The platform stores the export's hash beside the obligation.
2. Whoever writes a proof elaborates it with full Lean, and sends its export (the solution).
3. The Worker checks the solution with nanoda, permitting only `propext`, `Quot.sound` and `Classical.choice`. It then compares the solution with the pinned challenge, as Comparator does:
   - `obligation`'s type must be the same.
   - Every declaration that type uses, and every declaration those use, must be the same, so a proof can't change what a name means.

That trusts Lean's elaborator once for each statement, when it is pinned, as Comparator already does for each check. Writing statements directly as kernel terms would avoid that, but the kernel would then have to emit structures, their recursors and instances as Lean would.

The checker is its own repo, [lean-wasm](https://github.com/cronch-ai/lean-wasm), published as `@cronch/lean`, as z3-wasm is published as `@cronch/z3`: nanoda pinned, with its patch, the WebAssembly build, and a JS wrapper. Until the platform checks Lean proofs itself (step 6), `proofs/` runs Comparator with full Lean, as it runs Ethos.

## Not yet known

- **How far `grind` goes** on obligations with arithmetic, `seq.nth` or quantifiers.
- **How large exports get** for obligations bigger than T1's, and whether nanoda's 8 MiB stack is enough for them.

## Plan

Each step is its own issue and PR.

1. **Spike:** write the T1 obligations in Lean by hand, prove them, and report which tactics closed them. Done: see [the spike](#the-spike).
2. **`Cronch/Smt.lean`, with its lemmas, and the Lean printer:** `ruleObligations` with `format: "lean"`, and the Lake project.
3. **The checker:** `proofs/check-lean.mjs` over Comparator, with `proofs/lean.test.mjs` and the attacks above.
4. **T1 in Lean:** `proofs/t1.test.mjs` proves every obligation in Lean as well as with Ethos. Done: a Lean proof survives a new capability as an Ethos proof does. Whenever a query is the same to the byte, so is its Lean statement, and the proof is checked again, not re-proved.
5. **A checker for Workers:** [lean-wasm](https://github.com/cronch-ai/lean-wasm), nanoda for WebAssembly, with the comparison against a pinned challenge. See [Checking in a Worker](#checking-in-a-worker).
6. **Verdicts name their checker:** the platform pins each statement's export, checks proofs with lean-wasm, and records which checker accepted a rule's proof.
