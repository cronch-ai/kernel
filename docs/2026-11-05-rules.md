# Rules

Agreed on 2026-11-05, for T1 of the [north star](https://linear.app/cronch-ai/document/vhf-and-cronch-north-star-f5d662ad97c6): prove a harness cannot reach the network without permission, in a way anyone can check without Cronch, and add a capability without re-deriving the proof.

## Decisions

1. **The proof is over contracts, not a harness's step.** The interpreter checks a precondition at every call, so "this call can't happen until a person approves it" follows from the interface. It holds of every harness on that interface and for every model output. It assumes a compliant interpreter (F7). A harness with a bug has its call refused, which still means the unsafe behaviour can't happen. A proof that a harness never attempts the call is later work, if a property needs it.
2. **`unsat` is still not a verdict. A checked proof is.** cvc5 writes a proof in its CPC format, and Ethos checks it against the query. The kernel writes queries and takes no part in checking them, so `proofs/` could be replaced by anyone's.
3. **A rule names an operation and what approves it.** `ruleObligations` gives the queries: the initial grant, and each update that writes a field the precondition reads. See [rules.rs](../crates/kernel/src/rules.rs).
4. **Updates are read branch by branch.** The type inferred for an `if` keeps only the fields both branches give, and the interpreter writes whatever the taken branch gives. So what an update writes is read off its syntax, and one that can't be read is refused.
5. **A query holds only the part of the grant it reads or writes.** A capability that touches none of that part leaves the query the same to the byte, and its proof still checks. This is T1's "adding a capability should not mean re-deriving the proof".
6. **A formula the kernel can fail to evaluate is refused.** Assuming it evaluates would prove less than it says.
7. **A record's constructor is named apart from its sort.** SMT-LIB keeps them in separate namespaces, and Ethos doesn't.

## How a proof is tied to its query

Ethos's `--reference` flag doesn't check a proof's assumptions against the query. It accepted a sound proof of one query against the query of a broken contract, and said `correct`. A `(reference ...)` command inside the file does check them. So `proofs/check.mjs` writes that command itself, and allows a proof only the commands cvc5 writes, defining only its own `@t` terms, once each.

`proofs/rules.test.mjs` keeps the attacks: the wrong query, tampered and truncated proofs, forged assumptions and redeclared symbols.

One attack is accepted before that allowlist, and the cause is understood. With the `(reference ...)` command, Ethos accepts `(define <selector> () 0)` ahead of a proof, while the same define of a constant is rejected. Ethos's `define` of a name already in scope overloads it; it never replaces it. An overload is used only where it is selected as a term is parsed: for an applied symbol, the most recent overload that type-checks against its arguments; for an unapplied one, the most recent. A selector is only ever applied, so a nullary macro can't apply and parsing falls back to the real selector: the define is inert, and the assumptions still match the query. A constant is used unapplied, so the nullary macro is selected, and the assumption it changes is no longer among the query's assertions, which the reference check rejects. A define that is selected when the selector is applied breaks the proof the same way, so the distinction is whether the overload is selected, not selector versus constant. This define can't make Ethos accept a false statement: a sound proof carrying it, referenced against a `sat` query, is still refused. Overloads in general are another matter. Ethos also resolves them when it builds a rule's premises: a term defined under a premise's name is selected there, in place of the step it names, and the proof breaks.

So `check.mjs` doesn't leave any overload to Ethos. A proof may define only what cvc5 defines, a nullary `@t<n>` (no other definition appears in the 361 proofs the tests make), and nothing else in the proof may bind that name. No name a proof defines is then in scope already, whether the query's, the signature's or the proof's own, so there is nothing for it to overload. Ethos accepts an overload nothing selects, such as a definition of the signature's `@div_by_zero`; `check.mjs` refuses it anyway. Whether Ethos should stay the checker is decided with the Lean metatheory.

## What a proof rests on

- The interpreter complies with these semantics.
- Each contract states what its capability does.
- `when` says what approval means, and the operation it reads is really a person's answer.
- The rule names every operation that reaches what it protects. Nothing checks that today.
- The encoder: a query says what the rule says. A bug there gives a valid proof of the wrong statement, so the encoding belongs in the Pata spec.
- Ethos and its CPC signatures, which come from the cvc5 project: independent of Cronch, less so of the solver.
- Nothing adds to a grant except the contracts' updates, and the approving operation's answer is a person's, given now or earlier under a policy they set. Every run starts with the empty grant, by construction, so `initial` is always over it. See [Approvals](2026-11-05-boundaries.md#approvals).

## Limits

- **A rule says nothing about once, always or session.** It says a call can't happen until a person has approved it, and an entry stands for the rest of the run. How the host answers an ask is the host's. See [Approvals](2026-11-05-boundaries.md#approvals).
- **An update that writes what the precondition reads through a `fold` is refused.** A `fold` has no SMT-LIB reading. Giving one to the one-time `fold` in the test fixtures is out of scope.
- **A `Float` in a query can't be checked as the kernel computes it.** cvc5 answers `unsat`, and Ethos stops at the query: `Could not find symbol Float64`. An argument of `Float` stops it the same way when nothing reads it, because the query still declares it. A grant field no obligation needs is left out, and its proof checks. Spelling the sort and rounding mode as Ethos does isn't enough: cvc5's proofs about a double hold `trust` steps, so Ethos says `incomplete`. Nothing needs one yet.
- **A proof in the `real` reading says nothing about the kernel.** `ruleObligations` takes `floats: "real"`, and Ethos says `correct` of such a proof. It accepts a proof that `0.1 + 0.2` equals `0.3`, and the kernel computes otherwise. The proof doesn't show which reading it used, so that rests on whoever asked for the query.
- **cvc5 is the prover.** z3 didn't finish an approval step over lists within 120 seconds.
- **The tools install on Linux x86_64 only.**
